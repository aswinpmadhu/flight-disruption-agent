Appended to issue bodies according to each slot's `appends` list. These are the texts published in the Wave 1 issues.

## FOOT

**Workflow.** Claim only after the publisher announces "Claims open" in a comment on the pinned Backlog issue. Claim by assigning yourself and commenting "Claiming #n (rank r), my estimate h hours" (your own estimate). You may hold one issue in progress plus one awaiting review; the lowest-ranked READY issue (no `blocked` label) is claimed first, and you may skip one for a documented reason. Branch `feature/<n>-<short-name>`. The PR that completes the issue says `Closes #n`; every earlier PR **and every commit message in it** says `Refs #n` only. Do not mark a PR ready or merge it while any Blocked-by issue is unmerged. Never base work on another developer's unmerged branch. `pytest` passes on Python 3.13. **Every test name carries its test ID.** Edit only the files listed in this issue. After your PR merges, the merger removes `blocked` from each dependent whose prerequisites are met. Requirement changes are raised in this issue's discussion; the issue body is not edited silently. **Phase 1 rule:** this issue contains no delay or missed-connection behaviour, test or acceptance criterion. **Dormant-contract exception:** Phase 1 code may carry enum values, error codes, record types and the eighth tool's input model only if they have no behaviour; the only Phase 1 tests that touch such values are *negative boundary tests* (the Phase 2 capability is refused or unavailable, using existing frozen error codes, creating no state) and *contract-shape assertions* (a frozen enum member, error code or schema exists, or a parameter list is exact). They carry no Phase 2 test ID. Do not add others.

## SAFE

**Safety issue.** *Claim:* Safety Implementer Roster members only. A developer joins by commenting on the pinned Backlog issue "I accept: implementer / reviewer / both; I have read docs/03 §5.4 to §6.6 and this safety block"; nobody accepts for another person. The claim needs at least two other confirmed, available reviewers. *Cap (decision D-1, approved):* at most **three** safety issues per developer per product phase, and only **one** active safety issue per developer at a time. *Review:* a confirmed Safety Reviewer Roster member who is **not the author or a co-author** approves after the last push. *Preserve:* search consent and rebooking approval are separate records created only by their managers; `rebook(session_id, pnr, itinerary_key)` has no approval parameter; approval is single-use and invalidated when the selected option changes; the guard re-derives the plan on every call; denied calls are traced. **The tests under "Tests you own" are yours alone; do not skip, xfail or weaken any.** No change to a contract, requirement, error code, filter reason, marker list or threshold; if something is ambiguous take the stricter reading, record it in the issue, and park the item. *Takeover:* no push or draft PR within **90 minutes** of claiming, then the next roster member continues from the pushed work only; the PR is titled `[takeover]`; neither implementer may review it. *Safety merge audit:* at any freeze a table of every safety PR (author, approver, whether the approver was eligible) is posted on the pinned issue.

## PREP

**Preparation.** If this issue carries `prep-ok` you may prepare locally against the listed interface sources; a draft PR titled `[prep]` is allowed; **do not mark it ready or merge it until every Blocked-by issue is merged and `blocked` is removed.** Never build on another developer's unmerged branch. The provider re-posts its interface block when review changes it; rebase and re-check before marking ready. If an interface is undocumented, ask in the provider's issue.

## DK10

**`itinerary_key` contract (DK10).** Format: `<flight_number>:<YYYY-MM-DD>` per segment, in travel order, joined with `+` (for example `MD101:2026-12-01+MD205:2026-12-02`); `flight_number` matches `^MD[0-9]{3}$`; the date is the **scheduled departure UTC date**, never the estimated one; the key is opaque. **Roles, exactly:** B-01a defines the pure helper `derive_itinerary_key(segments)` and the `Itinerary` validator, both in `flight_agent/domain/models.py`; the validator uses the helper **only to verify** a supplied key (it compares the derived string with the supplied string and rejects a difference; it never parses a key and never replaces one); **B-08a (`flight_agent/services/alternatives.py`, later extended by B-08b) is the only production component that constructs a key**; **no other component constructs or parses a key**, and every other component compares exact strings; tests may call the helper to build expected values; `test_dk10_single_producer` (owned by B-01a) enforces this. B-04 enforces that `(flight_number, scheduled UTC date)` is unique across fixture flights; `get_flight_status(flight_number, date)` takes the scheduled departure UTC date.
